# GamerStore — Платформа цифровых товаров для геймеров

Production-ready веб-приложение магазина цифровых товаров (ключи, пополнения баланса Steam, подписки и гифт-карты) с гарантией однократной выдачи товаров в условиях конкурентных гонок (race conditions), отказоустойчивостью и безопасным восстановлением после сбоев.

## Ответы на ключевые вопросы ТЗ

### 1. Как обеспечили однократную выдачу (Exactly-Once Delivery)
1. **Дедупликация событий по `event_id`**: Таблица/реестр обработанных событий `processedEvents`. При повторном поступлении вебхука с тем же `event_id` система возвращает статус `ignored` и кэшированный результат без повторного списания ключа.
2. **Посегментная блокировка (`KeyedMutex`)**: Все операции над конкретным заказом (`order_id`) и промокодом сериализуются асинхронным мьютексом. 50 параллельных запросов выстраиваются в строгую очередь, исключая состояние гонки (race conditions).
3. **Конечный автомат состояний (State Machine)**: Заказ проходит строгие переходы `created -> paid -> delivering -> delivered`. Если заказ уже перешел в терминальный статус `delivered`, любые последующие вебхуки или повторные попытки выдачи немедленно возвращают ранее выданный ключ без списания новых остатков.
4. **Атомарное списание из пула**: Выбор и маркировка ключа (`isAssigned = true, assignedToOrderId = order_id`) выполняются атомарно внутри критической секции. Один ключ принципиально не может быть назначен двум заказам.
5. **Обработка событий не по порядку (Out-of-Order Delivery)**: Если вебхук оплаты пришел раньше создания заказа на бэкенде, платеж фиксируется в безопасном буфере ожидания `pendingPayments`. В момент создания заказа платеж мгновенно подхватывается, и товар выдается без задержек и дублирования.

### 2. Как воспроизвести проверку гонок
Проверку можно запустить тремя независимыми способами:
1. **Автоматические тесты Jest**:
   ```bash
   npm test
   ```
   Запускает 4 тест-сьюта (12 тестов), включая стресс-тест 50 параллельных вебхуков, гонки промокодов и идемпотентность повторной выдачи.
2. **CLI-скрипт проверки сценариев ТЗ**:
   ```bash
   npm run test:concurrency
   ```
   Выводит подробный лог прохождения всех 5 сценариев приемки с замером времени и валидацией ключей.
3. **В веб-интерфейсе (Live Runner)**:
   - Откройте приложение в браузере и нажмите кнопку **«Стресс-тест гонок»** в шапке сайта.
   - Нажмите **«Запустить тесты»** — система в реальном времени выполнит параллельные вызовы через API и отобразит метрики каждого сценария.

### 3. Сколько времени ушло по факту
- Фактическое время разработки: **4 часа 30 минут**.

## Архитектура и реализованные этапы

### Этап 1. Витрина и базовый флоу выдачи
- Верстка верхней части витрины по макету:
  1. **Баннер-карусель**: автоматическое переключение каждые 5 секунд, ручное переключение стрелками, интерактивные индикаторы-точки.
  2. **Кнопка «Каталог»**: открывает всплывающее меню с категориями; повторный клик или клик вне меню закрывает каталог.
  3. **Блок пополнения Steam**: интерактивный переключатель валют ($/₸/₽) с сохранением активного состояния, выбор номиналов (500 ₽, 1000 ₽, 2500 ₽), ввод логина Steam.
  4. **Ряд иконок сервисов**: Steam, Telegram, Roblox, Discord, PlayStation, Xbox, Spotify, YouTube с плавным выделением при наведении и фильтрацией.
  5. **Карточки товаров**: легкое выделение при наведении (подъем, акцент границы, тень), кнопка «Купить».
- Оформление заказа, модальное окно оплаты (вебхук-эмулятор), автоматическая выдача ключа и отображение кода с кнопкой копирования.

### Этап 2. Однократная выдача под гонками (Ключевой этап)
- Гарантия однократной выдачи при двойном клике, одновременных запросах и состязательных нагрузках.
- Сценарий с 50 параллельными вебхуками `status: "paid"` по одному заказу: ровно 1 вебхук выполняет списание, 49 дубликатов безопасно игнорируются, списывается ровно один ключ.

### Этап 3. Сбои и восстановление
- **Исчерпание остатков (`out_of_stock`)**: если пул ключей пуст, заказ не падает, а переходит в восстановимое состояние `out_of_stock` с сохранением факта оплаты.
- **Панель администратора (`/admin`)**:
  - Фильтрация заказов по категориям (включая список «Оплачен, но не выдан»).
  - Кнопка безопасной ручной повторной выдачи (`reissue`) после пополнения. Повторная выдача строго идемпотентна.
  - Форма пополнения пула ключей.
- **Симуляция внешних поставщиков (Supplier A & Fallback Supplier B)**:
  - Поставщик A: настраиваемый процент 5xx ошибок и таймаутов.
  - Поставщик B: резервный шлюз.
  - Сохранение выданного кода по `request_id`: при повторном запросе с тем же `request_id` поставщик возвращает тот же самый ключ (ловушка «таймаут ≠ отказ»).

### Этап 4. Промокоды с ограничением использования под гонками
- Промокоды из материалов ТЗ: `WELCOME10` (10%), `GG500` (500 ₽), `LIMIT3` (25%, макс 3), `ONCEONLY` (50%, макс 1).
- Серверный расчет скидки без доверия клиентским данным.
- Атомарный контроль счетчика `currentUses < maxUses` под параллельными гонками (из 20 одновременных запросов на `LIMIT3` ровно 3 получают скидку, остальные 17 отклоняются с ошибкой лимита).

## Стек технологий

- **Фреймворк**: Next.js 14 (App Router)
- **Язык**: TypeScript (strict mode)
- **Стилизация**: Tailwind CSS (стиль GitHub Dark / Linear: нейтральный цинк, границы `border-zinc-800`, отсутствие кислотных градиентов)
- **Иконки**: Lucide React
- **Тестирование**: Jest, ts-jest, tsx
- **Контейнеризация**: Docker, Docker Compose
- **Хранилище данных**: Транзакционный In-Memory Store с изоляцией мьютексами (соответствует требованиям Serverless Read-Only ФС на Vercel и обеспечивает мгновенные тесты без внешних СУБД).

## Запуск проекта

### 1. Локальный запуск через Node.js

```bash
# Установка зависимостей
npm install

# Запуск в режиме разработки
npm run dev

# Запуск тестов
npm test

# Запуск CLI проверки гонок
npm run test:concurrency

# Сборка production-билда
npm run build
npm start
```

Приложение будет доступно по адресу: `http://localhost:3000`.

### 2. Запуск через Docker Compose

```bash
docker-compose up --build
```
